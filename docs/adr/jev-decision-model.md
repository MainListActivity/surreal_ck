# ADR: 接入决策模型作为 AI 编排的结构化决策层

- **Status**: Accepted
- **Date**: 2026-09-22
- **Scope**: `server/ai/**`、`server/src/ai/**`；首个接入点为 Router workflow 意图分类

## Context

Router workflow 的**意图分类**目前依赖一次完整生成式 LLM 调用：长 system prompt 生成 JSON plan，再 `JSON.parse` + zod 校验，失败兜底 chitchat。现状问题：

1. **延迟**：一次秒级生成式调用只为产出一个类别决策；**流式进度通道**只能掩盖、不能消除。
2. **成本**：分类是固定高频小动作，按生成 token 计费不值。
3. **没有置信度**：LLM 输出只有结果没有校准概率，低置信与明显错误无法区分，无法做分级门控。
4. **同类决策点在增多**：写操作风险分级、导航候选消歧、风险评分、虚拟员工派单决策等都是"结构化判定"，每个都挂一次 LLM 会放大以上三点。

TypeSafe Jev 是 System One 类模型（本文称 **决策模型**）：输入决策输入 + **类型化问题**（noul / choice / score），输出每个选项的校准概率与 **决策置信度**，不生成文本；典型延迟约百毫秒，成本比生成式低约两个数量级。

## Decision

在 server 侧实现与 `llmCaller` 平行的 **决策模型** 薄封装（fetch + zod 校验，单一 endpoint，env 控制启停；`TYPESAFE_API_KEY` 缺省即纯 LLM 路径，与 `AI_API_KEY` 缺省不接线同一模式）。封装按通用接口设计，后续写确认、消歧、评分等接入点复用同一 client。

首个接入点为 Router workflow **意图分类**：一次**决策请求**并行问「多意图」(noul) 与「类别」(choice，5 个现有类别；`chitchat` 已承担兜底语义、不加 other)。决策输入为用户消息原文 + 紧凑 `AiContextSnapshot`。消息为单意图且**决策置信度** ≥ 阈值（默认 0.75，env 可调）时走**单意图捷径**——以原文为子任务描述生成单步**路由计划**；否则进入 **LLM 回退**。Jev 错误/超时（默认 1.5s）一律静默回退 LLM，不阻断 chat。每次决策调用输出一条结构化日志（模型版本 / 答案 / 决策置信度 / 是否回退 / 延迟），供事后评估。

### 硬边界

- 决策模型只做结构化判定，不生成任何面向用户的文本。
- 决策置信度只用于门控分流，不作为正确率承诺。
- 决策模型的概率输出不能直接成为授权、扣账、DDL 或任何不可逆操作的唯一依据；配额、权限、账本维持确定性代码路径。
- API key 只在后端持有。

## Considered Options

- **用 Jev 全量替换意图分类**：不可行——决策模型不生成文本，产不出有序**路由计划**与多意图消息的子任务切分；只能做捷径 + 回退。
- **shadow 模式先观察一致率**：POC 阶段让每条消息同时付 LLM 和 Jev 两次调用，成本翻倍不值；改为 env flag 直切 + 结构化日志，事后用日志评估一致率。
- **官方 `@typesafe-ai/sdk`**：server 依赖极少，单一 endpoint 不值得引入新包；薄 fetch 封装 + zod 与仓库风格一致，接口自缚便于以后替换。

## Consequences

- 未配置 `TYPESAFE_API_KEY` 的环境行为与现状完全一致。
- 单意图高置信消息的路由延迟从秒级降到约百毫秒；**多意图消息**与低置信消息延迟不变（仍走 LLM）。
- 后续写操作风险分级、导航候选消歧、风险评分、虚拟员工派单决策复用同一封装，不重复造 client。
