# 持续采集公开案例、更新中国大陆法规并建立法条关联

Parent: [`律师行业订阅与平台法律数据产品决策地图`](../PRD.md)

## Scope

- 首期法规范围为中国大陆；具体规范类型、效力层级和来源清单在来源调研中确定。
- 案例覆盖可获取公开裁判文书的各类案件，不限定破产领域；不承诺已经覆盖全部公开文书。
- 用户明确要求程序化持续获取案例、更新法规，并建立案例与法规关联。本票扩展原地图仅定义来源契约的范围，但仍处于规格阶段。
- 复用 05 的来源许可、不可变内容版本、staging、发布身份和 06 的精确版本引用。

## Pipeline proposal

> 已确认调整：首期采用本地 agent 采集成品后经 MCP 提交。本节原有服务端爬虫与完整页面流程保留为后续候选，不再作为首期必须交付项。首期决定见文末。

### 1. 来源接入与调度

- 每个来源独立适配器，记录官方入口、允许获取方式、许可核验结果、覆盖范围、时区、调度频率、请求预算和解析器版本。
- 先验证真实样本、获取可行性与使用条件，再启用生产调度。登录、验证码或访问限制不能通过绕过方式解决；不可用来源暂停并记录原因。
- 持久化任务队列与调度状态支持进程重启、互斥领取、租约续期、超时回收和幂等重试；调度程序属于产品基础设施，不依赖对话任务持续在线。
- 全量历史回填和持续增量任务分开排队，增量优先，回填遵守相同来源限速。
- 频率按来源能力配置，初始可采用每日检查建议值，实际启用前验证；页面显示最近成功检查时间及真实覆盖范围，不承诺实时全量。

### 2. 发现、获取与去重

- 按来源游标或更新时间增量发现；没有可靠增量接口时采用有界列表扫描、重叠时间窗口和周期复查。
- 任务身份包含来源、源文书标识和源版本/内容指纹。重复抓取不能产生重复案例或重复发布。
- 游标只有在该批候选全部获得持久化处理状态后推进；单条失败保留独立重试任务，避免遗漏。
- 在许可允许范围保存来源 URL、获取时间、HTTP 元数据、原始内容哈希和必要原始快照；保留解析器版本以支持重新解析。
- 文书案号不单独作为唯一身份：同案可能有多个审级和文书。跨来源去重结合文书类型、法院、日期、案号及正文，歧义进入待核验队列。

### 3. 法规与法条版本

- 分开记录公布时间、生效时间、失效时间、来源更新时间和采集时间；未知值保留未知。
- 新公布、修订、废止、勘误形成可追溯事件；正文变更生成不可变新版本，历史版本不覆盖。
- 法规稳定身份、法规版本、法条版本分开建模；条号调整需记录映射，不能假定不同版本的同一条号内容相同。
- 页面抓取失败或单次 404 不自动判定法规废止、文书撤回。法律效力及撤回状态需有来源证据。
- 新法规版本发布后触发受影响索引更新及待核验关联重算；历史报告引用继续固定原版本。

### 4. 案例与法规关联

- 提取文书明确引用的法规名、条号、原文位置、上下文和引用主体，区分法院依据与当事人主张。
- 名称规范化和版本候选解析优先使用确定性规则；必要时使用模型辅助，保留模型/规则版本及证据，结果不可直接冒充法院引用。
- 结合文书明确版本信息、案件事实时间及适用说明解析法条版本；不能只按裁判日期或当前最新版本强行匹配。
- 关联状态区分已解析、存在歧义、未找到；保留候选和原因，支持人工核验。无法关联的文书可先发布并显示关联不完整。
- 系统分析出的相关法条单独标记为推断关联；不得混入法院裁判依据。
- 关联有引用主体、定位、证据、解析版本和核验生命周期，是独立业务实体；具体 SurrealQL schema 待真实样本验证后设计。

### 5. 校验与发布

- 依次执行来源许可、结构完整性、正文质量、去重、版本和关联校验；问题数据进入隔离区。
- 发布通过受限 content_publisher 身份执行；采集和发布不使用客户 workspace 数据库，不计入客户自建容量。
- 发布固定版本及批次清单，正文与检索索引就绪后才推进可服务版本；部分失败不公开半成品。
- 发布事件触发搜索索引、授权读取投影和缓存更新。撤回先停止服务，再清理索引及缓存；保留最小审计记录。

### 6. 运维入口与恢复

- 独立 ops 应用提供来源状态、最后成功时间、检查/新增/更新/重复/失败数量、积压及法条关联待核验数量。
- 支持暂停来源、重试批次、重新解析、审核关联与撤回发布；每次人工动作有责任人和原因。
- 监测来源长期无成功采集、解析失败激增、任务积压及索引发布失败；无新增数据不等于故障。
- 外部网络请求与数据库事务分离；使用持久化检查点和幂等发布恢复，不依赖跨网站与数据库的事务。

## Acceptance scenarios

- 同批任务重复执行、进程中途重启和多 worker 领取，不重复入库、不漏掉失败条目。
- 历史文书迟到发布能被重叠扫描发现；同案不同文书不被误合并。
- 法规修订生成新版本，旧案例与历史引用仍能指向正确旧版本。
- 条号歧义和无法确定版本进入待核验，系统推断不会标为法院依据。
- 来源不可用、许可停止、撤回和索引失败各有明确处理状态及恢复路径。

## Operator data workbench

用户要求通过运营页面方便快捷地从互联网维护数据，覆盖采集、清洗与审核。数据工作台位于独立 `ops/` 应用，任务由后端持久化执行；浏览器关闭后任务继续运行。

### 1. 三个主要页面

| 页面 | 首期操作 |
|---|---|
| 来源与采集 | 管理已接入来源、粘贴受支持来源的文书/法规 URL、按日期范围和来源支持的条件采集、启动历史回填、开启或暂停持续更新 |
| 批次工作台 | 查看进度和失败原因、对照原文与清洗结果、批量应用清洗规则、预览差异、重新解析、重试失败项 |
| 审核与内容库 | 筛选待审核项、核对法条关联和版本、批量通过/退回、发布、查看历史版本、纠错和撤回 |

### 2. 从互联网到发布的页面流程

1. 运营选择已接入来源或粘贴链接；系统识别适配器，展示可采范围、预计任务规模和采集条件。未知站点进入来源接入待办，不承诺任意 URL 均可一键采集。
2. 运营启动采集，获得可返回查看的批次任务；手动任务和周期任务使用相同队列、去重、重试及审计机制。
3. 自动解析、标准化和去重后，界面显示新增、重复、内容更新、解析异常与关联待核验的数量。
4. 运营在原文与结构化结果对照页检查清洗效果，可选择规则并预览受影响记录，再保存新处理版本。
5. 审核列表支持按错误、来源、类型和关联状态筛选；提供逐条审核及可预览范围的批量审核。阻断性错误不能通过批量操作跳过。
6. 审核通过的数据进入待发布队列；运营可通过“通过并发布”合并两步操作，但内部保留独立审核与发布记录。发布完成后客户检索才可见。

### 3. 清洗与审核边界

- 首期提供固定清洗动作：页面导航/广告噪声去除、空白和编码规范化、日期格式统一、来源字段映射、法规名称标准化、重复候选处理；不用自由代码编辑器作为日常入口。
- 原始获取证据保持可追溯；清洗不得静默改写案情、裁判结论、法条正文或来源原始表述。人工纠错保留前后差异及原因。
- 模型可提出结构化抽取、法条关联和异常提示，运营看到原文定位与候选；模型生成的补充内容不能冒充来源正文。
- 文书中的法院引用、当事人主张、系统推断在界面明确区分；关联不确定时允许保留待核验状态，不能自动生成无证据的确定关系。
- 已发布内容的再次清洗或人工修正生成新版本并重新审核；支持按批次重新处理，原有发布版本和历史报告引用保留。
- 首期新增和变更内容经人工审核后发布，可批量审核；自动采集和自动清洗不等于自动发布。未来自动发布策略另行定义。

### 4. 权限与执行

- 采集、审核和发布属于平台运营的独立能力，可授予同一运营人员，首期不要求双人审批。
- `ops/` 调用受保护后端接口；抓取、解析、模型处理和发布在后台任务中执行，不在浏览器持有来源凭证或 publisher secret。
- 来源 URL 在后端校验协议、目标域名和重定向；抓取 worker 不得访问内网、回环或云元数据地址，避免粘贴链接成为访问内部服务的入口。
- 新来源仍需适配器接入和许可核验，页面可收集来源信息和提交接入请求；首期不建设任意网站可视化爬虫编排器。

## Decision: MCP-first content maintenance

用户已确认采用“本地 agent 采集清洗 → MCP 提交 → 服务端校验与差异 → 运营确认发布”。采集架构已确定；本票继续 in_progress，直到真实样本、数据契约和 MCP 工具边界落实。

### 已确认：最小成品数据要求

| 类型 | 提交必需 | 可后续补充 |
|---|---|---|
| 共通 | 来源、原始链接、采集时间、标题、正文、来源记录标识或内容指纹 | 原始附件、清洗说明 |
| 法规 | 发布机关、规范类型；版本无法确定时明确标记待核验 | 文号、公布/生效/失效日期、效力状态、修订关系 |
| 裁判文书 | 文书类型；案号、法院缺失时明确标记待核验 | 裁判日期、案由、审级、程序类型、结构化裁判结果 |
| 法条引用 | 每个已提取引用的文书原文、位置、引用主体 | 匹配的法规版本和具体条款 |

- 未知值留空并保留原因，agent 不得为了通过格式校验推测案号、日期、发布机关、引用主体或版本；未知引用主体可显式记录为未知。
- 无明确法条引用的文书允许提交空引用集合；引用提取尚未完成与已检查但无引用分别记录。
- 清洗正文与来源证据分开保留，来源证据按许可允许范围留存并可追溯；原始附件不作为每次提交的必填项。
- 服务端自行计算接收正文/证据的哈希并校验客户端声明；哈希说明数据一致性，不代表服务端已经独立核验来源真实性。
- 来源记录标识用于追踪来源，不把案号单独作为文书唯一键；内容指纹由服务端复算。
- 未匹配法条不阻止案例进入待校验批次，可保留关联待核验；不得展示为已核验的裁判依据。
- 提交成功仅表示批次已接收，不立即对客户可见；发布门槛按内容类型给出逐项错误或警告。可留空字段不在本次默认全部升级为发布必填字段，具体门槛需在样本验证时固定。
- 本次只确认逻辑字段与未知值规则；字段命名、传输类型、大小限制和数据库 schema 在契约阶段落实。

### 已确认：内容实体与整份提交

| 分组 | 逻辑实体 | 职责 |
|---|---|---|
| 法规 | 法规、法规版本、法条版本 | 固定法规身份与历次正文修订，引用精确条款版本 |
| 案例 | 裁判文书、文书版本、法条引用关系 | 固定文书身份，保留变更及有证据的引用关联 |
| 维护流程 | 来源、提交批次、批次条目、校验结果、发布记录 | 接收、去重、逐项校验、部分发布、修订与审计 |

- 用户已确认本地 agent 提交完整的一份法规或裁判文书，由服务端拆分内部记录；客户端不指定数据库表名、不构造数据库 RecordId、不逐条调用创建法条。
- 逻辑实体复用 05 的 content_source、content_item、content_version、许可与发布模型；上述分组不是要求再建一套平行目录。法规/文书的专属属性与通用内容目录如何物理映射，留在 schema 规格落实。
- 平台来源、法规、文书及其维护记录放在平台内容数据库；客户工作区只保存用户收藏、批注、研究成果与引用指针，商业权益仍属于 _system。
- 法条引用是独立业务关系，包含原文、定位、引用主体、目标版本、解析来源与核验状态；不能仅以法规 ID 数组替代。文书没有明确引用时不强制构造关系。
- 法院明确引用、当事人主张和系统推断须可区分；同一法规在不同段落、不同主体下可有多个引用，不能去重成单个无上下文关系。
- 一份法规版本及必要法条拆分结果作为一致的发布单元；拆分不完整不得把缺损版本标为完整。外部接口保持版本化的数据契约，内部表结构演进不要求客户端跟随修改表名。

### 已确认：去重与版本识别

- 同一来源记录与相同规范化正文、实质元数据再次提交，标记重复，不新增发布版本；采集事实仍可记录。
- 同一来源记录正文或实质元数据变化，生成候选新版本，展示差异后发布；当前来源 URL 与历史版本均保持可追溯。
- 不同来源的疑似同一文书只产生合并候选；首期不因案号相同或语义相似自动合并，明确核验后才归到共同稳定身份。
- 同案不同审级、不同文书类型分别建文书身份；法规修订归入法规的不同版本，新旧法条按版本关联。
- 单纯采集时间变化不触发内容新版本；清洗规则改变导致正文差异需要审阅，并标记为平台处理修订，不冒充来源修订。
- 用户已确认本节规则；相同来源更新、跨来源核验及平台处理修订均保留来源证据和审计。

### 已确认：通过现有工具纠错、撤回与恢复

- 保持五个 MCP 工具数量不变，submit_batch 的条目表达新建/修订、撤回、恢复三类操作意图；服务端按意图区分校验与权限。
- 纠错提交关联当前版本的候选新版本，展示差异，发布后推进当前版本；原版本和历史引用不被静默覆盖。
- 撤回条目指定目标内容/版本、当前版本前提及原因；发布该操作后停止目标内容的客户检索、全文读取与新的 AI 使用，保留最小引用标记和审计。撤回不等于物理删除。
- 恢复重新校验来源许可、发布状态与索引准备情况；通过后恢复指定有效版本，不直接撤销过去的撤回记录。
- inspect_batch 展示操作类型及影响范围，publish_batch 只执行明确审阅的意图与目标；修订前提已变化则拒绝执行并要求重验。
- 首期不在 MCP 中提供物理删除内容或任意执行数据库语句的工具；依法删除等要求由独立受控运维流程处理。
- 用户已确认本节规则，五个工具数量保持不变。撤回/恢复条目引用目标身份及版本前提，不要求重复上传正文；最小成品正文要求适用于新建/修订。

### 首期 MCP 工具明细

- `get_data_contract`：读取契约版本、必填项和格式示例。
- `search_content`：按来源标识、法规名、案号等检索已存在内容及版本，辅助去重和关联；权限限于平台数据维护范围。
- `submit_batch`：携带契约版本、幂等键和数据提交批次，返回批次标识；同键同内容复用结果，同键不同内容报冲突。
- `inspect_batch`：返回处理状态、逐条问题、待核验关联和新增/更新/重复差异；异步校验时可重复查询。
- `publish_batch`：只发布运营已经审阅的固定批次及其校验修订；内容或校验依据变化后要求重新校验与审阅。重复调用不重复发布。
- 首期修正通过提交关联前一批次的新修订实现，旧批次与审核证据不覆盖。服务端重新检查当前来源资格及发布权限。
- 用户已确认上述五个工具作为首期范围；尚未实现。具体参数、返回值和错误结构在实施契约中固定。

### 已确认：批次部分失败与发布

- 批次校验区分阻断错误、非阻断警告和正常记录；未确定法条关联通常为警告，缺少正文或必要来源信息为阻断错误。
- `inspect_batch` 固定校验修订，返回可发布记录清单、阻断清单和警告；默认不静默忽略错误。
- 运营可明确选择“仅发布本次校验通过的记录”；`publish_batch` 接收固定校验修订及明确记录清单，不因后台新校验自动扩大发布范围。
- 存在警告的记录在审阅时明确展示，发布后保留待核验标记；阻断记录留在原批次，可关联新批次修正后重新提交。
- 发布结果逐条说明已发布、重复未变和失败；中途失败按相同发布请求幂等重试，不重复创建内容版本，也不把整个批次错误标为成功。
- 原子性以单个内容版本及其必需依赖为边界；某项依赖的法规版本未就绪时，引用保持未解析或该发布项被阻断，不生成指向不存在版本的关联。
- 用户已确认允许按明确清单部分发布。

### 已确认：OAuth 与平台运营身份

- 数据维护 MCP 采用受 OAuth 保护的远程 HTTP 接口；本地客户端通过授权码与 PKCE 代表真人运营获得访问授权，不分发共享 API key 或数据库 root。
- MCP 与 ops 使用相同的平台运营资格判定：可信身份对应有效 platform_operator 才能接入；普通客户、工作区管理员、计费管理员或仅能完成 IdP 登录的账号不会自动获得权限。
- 每个工具请求验证 token 的签名、issuer、有效期、面向 MCP 的 audience/resource 和所需 scope，并重新查询当前运营状态及工具所需能力。实际权限取 OAuth 授权与当前平台能力的交集。
- 登录运营端资格是维护数据的必要条件；现有细分能力继续适用，只有配额管理权限的运营不自动获得内容发布权。同一人可被授予读取、提交和发布能力，不要求双人审批。
- 运营被禁用或数据能力被撤销后，后续工具调用立即拒绝，不依赖旧 token 自然到期。异步发布在执行前复核授权；已完成发布保留，不因身份撤销自动删除。
- OAuth 授权确认表示客户端可代表该运营调用工具，不代替具体批次审阅；publish_batch 仍绑定已审阅的校验修订与记录清单。
- 提供 MCP Protected Resource Metadata 及授权服务器发现，按选定协议版本实现 resource 参数和受众验证。不把客户 workspace 的数据库 token 直接作为 MCP 授权，也不将 MCP token 透传数据库。
- 使用相同 IdP 的账号体系不要求各客户端共用 clientId；ops SPA 与本地 MCP 客户端的注册、回调、PKCE 和 audience 按协议配置。需验证现有 IdP 支持情况及跨客户端 subject 映射，禁止按未经验证的邮箱合并身份。
- 纯运营 OAuth 登录不要求 db/ac 或客户工作区成员资格；现有 default-scope hook 必须适配此类授权请求，不签发 _system 管理员数据库权限作为替代。
- 持续采集客户端只在 OAuth 授权及运营资格有效时运行；撤销授权或刷新失败时停止远端提交并提示重新授权。
- 实施依据：[MCP Authorization 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)。传输库、IdP 配置和客户端互操作需实测后落实。

### 已确认流程的执行分工

#### OAuth 接入核查与首期建议

- 已完成 [现有 IdP 核查](../research/idp-mcp-oauth-readiness.md)：PKCE/public client/public sub 有基础；公开动态注册需要管理凭证，resource/scope 完整互操作尚未验证。
- 已按用户要求确定同 issuer、ops 独立 client、MCP 动态客户端注册（DCR）；运营登录不挂 workspace db/ac/RL claim hook，MCP 采用专用 audience。不向客户端下发 IdP 管理凭证。
- DCR 为首期必做，替代此前预注册优先建议。动态客户端按受限 public client 创建，不允许自授 trusted/skip-consent、数据库 claims、任意 audience 或运营能力。
- `resource`、scope 限制、第三方授权提示、刷新和客户端回调验证列为实施依赖；客户端注册成功不代表获得数据权限，仍需有效运营账号授权。
- 验收必须用未预注册的 Codex 客户端从 MCP URL 完成发现、动态注册、浏览器授权和工具调用，不能用预置 clientId 或手工 token 替代。
- 本次仅核查，未修改 ma_hono 或线上 IdP；跨仓接入修改应在实施任务明确列出。

- 本地 Codex 或其它兼容 MCP 的客户端负责网站浏览、下载、提取和清洗，提交统一的法规/文书数据包。具体客户端的远程 MCP、鉴权及文件传输能力需在接入时验证，不假定所有客户端相同。
- 服务端提供窄数据维护 MCP：读取数据契约与来源信息、提交幂等批次、校验并返回逐条问题、查看差异、发布指定已校验批次、读取处理结果。工具命名和传输格式在实施时固定。
- 成品数据包携带来源 URL、取得时间、来源标识、正文/证据哈希、文书或法规结构、版本信息、引用定位及采集处理说明；未知版本或法条关联显式标为待核验。
- 服务器执行 schema、来源资格、去重、版本一致性和引用证据校验。模型自称“已清洗”不能替代校验。运营可在本地对话审阅结果后调用发布工具，无需首期建设完整审核页面。
- 校验结果绑定批次内容哈希；内容变化必须重验。发布只接收固定批次标识和版本，不在发布时接收未经验证的新正文。
- 首期不要求双人审核；提交与发布仍分别保留身份、时间及结果记录。具备运营身份不自动获得任意数据库查询或 DDL 能力。
- MCP 复用受限内容发布能力；不得把数据库 root 交给采集 agent。复用 SurrealDB 原生 MCP 还是薄应用 MCP，需验证原生工具权限能否完整承载这组领域动作后确定，默认优先窄应用 MCP。
- 新网站只要能由本地 agent 获取并转换为既定契约，通常不需要服务端改代码发布；新增来源记录与许可配置仍需维护。新增数据类型或契约变更可能需要服务端升级。
- 周期采集可由运营控制的本地 runner 或常驻 worker 使用相同 MCP 执行；必须具备持久化检查点、重试和运行日志。本地设备离线时不保证持续更新；本次不创建对话自动化或启动实际调度。
- 原完整来源适配器平台、可视化清洗编辑器、批量审核页面和服务端通用抓取器后置。ops 首期只需维护访问权限、批次状态和审计入口。
- SurrealQL 可承担已入库结构化数据的规范化与校验；HTTP 获取结构化接口是可选能力，不将数据库内 HTTP 请求视为能自动完成浏览器交互、任意页面解析和持续调度的采集系统。
